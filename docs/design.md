# 设计

这份文档说明控制台要做成什么样、为什么。想看实际效果，按[预览指南](install/preview.md)用示例数据跑起来。

## 给谁用

控制台给 operator：部署 dsh-superagent、对它说的话负责的那个人。团队成员在 GitHub 和飞书里和 agent 打交道，不需要新界面。

由此定一条边界：**团队的注意力由 agent 在原渠道里负责，operator 的注意力由控制台负责。** 控制台不重复 agent 已经在渠道里说过的事，只对系统级问题提醒。

## 价值从哪来

> 它的价值 = 它做成的有用工作 − 它占用的注意力（团队的 + 你的）

原型已经在系统层面解决了并发、路由、上下文和故障恢复。剩下卡住价值的地方都在人这边：

1. 你回应得多快：每个 Ticket 卡在“等你回答/评审”的时间，都是产出在流失。
2. 你敢不敢让它主动干：主动性是 super agent 价值上限最高的部分，但原型要求从观察模式开始。
3. 它出错时你能不能马上纠正：行为写在提示词里，每个 Session 用的提示词版本都有记录。
4. 你能不能看懂它：不理解就不敢放权。
5. 你能不能发现它还能做什么：很多能力散在不同设置块里。

## 六个闭环

| 闭环 | 频率 | operator 的问题 | 承接的页面 |
| --- | --- | --- | --- |
| 解阻 | 每天多次 | 什么在等我？ | 首页 |
| 理解 | 随时 | 它为什么这么做？为什么没理这条消息？ | Ticket 工作台、消息去向 |
| 信任 | 每周 | 能不能放手让它主动干？ | 校准、洞察 |
| 调教 | 出问题时 | 它太啰嗦或做过头了，怎么改？ | “这次表现不对”、提示词、策略 |
| 扩展 | 每月 | 还能让谁、在哪里用上它？ | 场景配方、被拦下的请求、来源 |
| 保障 | 异常时 | 它还正常吗？ | 健康 |

## 体验原则

- **默认安静。** 一切正常时首页几乎为空；数字只在会改变你行为时出现；数量等于它链接到的列表长度。
- **先说人话。** 列表上写“等你回答”“在等新消息”；Trigger、Mandate 这些术语放进详情。
- **每个判断都能解释。** 任何 Ticket、任何被忽略的消息，一步就能看到准入、评估、规则和结论。
- **在哪看到就在哪处理。** 操作在行内，修复动作和问题在同一屏。
- **改之前先看影响。** 策略、规则、提示词保存前，列出会影响什么。
- **从意图出发。** 场景配方把散落的能力组合成“想让它做的事”。
- **危险操作要确认。** 停止会撤回授权，暂停会停下所有派工，都在页面内确认。
- **为远程预留。** BFF 是唯一入口，每个操作都有风险等级；布局从一开始就适配窄屏。

## 页面

| 页面 | 作用 | 阶段 |
| --- | --- | --- |
| 首页 | 下一步；需要你的 Ticket，等得最久的在前；系统问题 | M0 |
| 健康 | 来源、执行器、全部问题、暂停处理、24 小时流量、控制台操作记录 | M0 |
| 看板 | 按阶段排开所有 Ticket（排队、执行中、需要你、等新消息、最近结束） | M1 |
| Ticket 工作台 | 请求、判断、派工、报告、后续消息、结束合成一条时间线；为什么它能做；关注的线程；执行信息；worker 在做什么、它说了什么 | M1（调教入口在 M2，worker 记录和消息在 M3a） |
| 消息去向 | 粘贴链接、`#123` 或几个字，看一条消息经过的每一步；线程列表与线程页；重新评估、退订 | M1 |
| 校准 | 复核“本会接单”的判断，按规则看一致率与日均量，预览切到自动 | M2 |
| 场景配方 | 从意图出发，一次配好来源、策略、规则、提示词 | M2 |
| 策略 | 主动接单模式、名单、准入矩阵、规则、bot 列表，保存前看影响 | M2 |
| 提示词 | 团队段落、skill、内置覆盖、默认更新的差异、完整提示词、历史 | M2 |
| 洞察 | 等你的时间、Ticket 结局、被拦下的请求、排队时间；它对外说了多少话 | M2（发言量在 M3a） |
| 来源、执行 | 来源配置、账号、从机器人所在的群里选群；并发、模型、prepare 命令、部署限制 | M2（账号、选群、部署限制在 M3b） |

## 路线图

**现阶段的重点：先把 dsh-superagent 已有的能力用好。** 派活走飞书（以后加上 GitHub）暂时够用，所以“控制台作为派活来源”（在控制台里提需求、回答 agent 的提问）先放一放，排在后面，需要时作为一种新的来源再做。

| 阶段 | 内容 | 需要改上游吗 |
| --- | --- | --- |
| M0 | BFF（本地访问模式、风险分级、审计）、上游类型镜像、mock、SSE、外壳、首页、健康 | 否 |
| M1 | 看板、Ticket 工作台、消息去向、命令面板、全部操作。按 URL 在 DSH Web 里打开 worker Session 的小插件推迟了，后来由 M3a 的“worker 在做什么”取代 | 否 |
| M2a | 校准（标注存在控制台自己的库里，按规则算一致率和每天命中次数）、策略（名单、bot 列表、准入矩阵、规则、主动接单模式、保存前看影响、修改历史） | 否 |
| M2b | 提示词（团队段落、skill、内置段落覆盖、默认已更新的对比、按角色组装的完整提示词、历史）；Ticket 工作台的“这次表现不对？”：选出问题，看 worker 当时用的提示词版本，直接给负责的段落加一句 | 否 |
| M2c | 场景配方（静默复现修复、支持群、依赖升级跟进、新 issue 分诊、跨平台身份）、洞察（等你的时间、结局、被拦下的请求、容量和 7 天趋势）、来源（接收开关、飞书群）、执行（并发、模型、目录、prepare、禁用命令、评估时限） | 否 |
| M3a | companion 插件（DSH 插件，装进 superagent profile）：Ticket 工作台的“worker 在做什么”（会话记录，运行中自动刷新）和“它说了什么”；洞察的发言量（按 Ticket 统计，因为上游的发送记录没有时间） | 否（独立插件） |
| M3b | 补齐上游已有、控制台还没提供的：重新检查配置（`setup/check`）、从机器人所在的群里选群并刷新群列表（`sources/:id/labels`）、在来源页改账号（仓库、agent 的 GitHub CLI、机器人的 lark-cli；先检查再保存，通过后重启）、只读显示部署限制；setup 问题用上游面板的中文措辞 | 否 |
| M3c | 执行页切换正在运行的主 Session 的模型：上游只在 Session 第一次调用模型前写入模型，由 companion 调 DSH 的 `selectModel` | 否（独立插件） |
| M3d | 工作目录页：每个 Ticket 目录占多少磁盘，逐层看里面的文件，在访达中显示。这一版只看不改，删除要先处理 Ticket 被恢复时目录和分支的问题 | 否 |
| M4 | 远程与手机：tailnet 访问模式、passkey 设备配对、PWA、推送 | 否 |
| 暂缓 | 控制台作为派活来源：在控制台里提需求、直接回答 agent 的提问。dsh-superagent 允许外部插件注册来源（飞书来源就是这样接入的），可以由 companion 注册 | 否（独立插件） |
